## คืนก่อนส่งงาน

ทีมสี่คนทำเกมทายคำศัพท์ส่งงานวันวิทยาศาสตร์ ต่างคนต่างแก้ไฟล์ในเครื่องตัวเองแล้วส่งต่อกันทางแชท คืนก่อนส่ง มีไฟล์ชื่อ `เกม_final.py`, `เกม_final_จริง.py` และ `เกม_final_จริง_v3.py` ไม่มีใครรู้ว่าไฟล์ไหนล่าสุด ส่วนตัวนับคะแนนที่ต้นเขียนเสร็จเมื่อวานก็หายไป เพราะฟ้าบันทึกทับ ปัญหานี้เกิดจาก **ทำงานเป็นทีมโดยไม่มีวิธีและเครื่องมือ** บทนี้ต่อจากบทกระบวนการพัฒนาโปรแกรมแบบวนรอบ

## บทบาทในทีม

ทีมพัฒนาซอฟต์แวร์มักแบ่งบทบาท เช่น

- **ผู้แทนผู้ใช้** รวบรวมความต้องการและตัดสินว่าอะไรสำคัญก่อน
- **ผู้ออกแบบ** ออกแบบหน้าจอและประสบการณ์ผู้ใช้
- **นักพัฒนา** เขียนโปรแกรม
- **ผู้ทดสอบ** เขียนกรณีทดสอบและหาบั๊ก
- **ผู้ประสานงาน** ดูแลแผน นัดประชุม และช่วยแก้สิ่งที่ขวางทีม

นักเรียนคนหนึ่งอาจรับหลายบทบาท และควร **สลับบทบาท** ในแต่ละโครงงานเพื่อฝึกให้ครบ

## แบ่งงานและวางกำหนดเวลา

แตกโครงงานเป็นงานย่อยที่เสร็จได้ใน 1–2 วัน ประมาณเวลา ระบุผู้รับผิดชอบ และดูว่างานใดต้องรองานใด แล้ววาดเป็น **แผนภูมิแกนต์** (ดูภาพ) งานที่ไม่ต้องรอกันทำพร้อมกันได้ โครงงานจึงเสร็จเร็วกว่าการบวกเวลาทุกงาน แต่ไม่เร็วกว่าเส้นทางที่ยาวที่สุดของงานที่ต้องรอกัน

ทีมแบบ **agile** ทำงานเป็นรอบสั้น เช่น รอบละหนึ่งสัปดาห์ ใช้ **บอร์ดงาน** สามช่อง ต้องทำ → กำลังทำ → เสร็จ ทุกคนเห็นว่าใครทำอะไรอยู่ คุยสั้น ๆ ทุกวันว่าทำอะไรและติดอะไร และทบทวนท้ายรอบว่าอะไรควรปรับ

แผนที่ดีต้องคิดถึง **ความเสี่ยง** ด้วย ให้คะแนนโอกาสเกิดและผลกระทบ (เช่น 1–5) คูณกันเป็นคะแนนความเสี่ยง แล้ววางแผนรับมือเรื่องคะแนนสูงก่อน และระบุว่าใครรับผิดชอบ เช่น ไฟล์หาย → ใช้ระบบควบคุมเวอร์ชัน สมาชิกป่วย → ให้มีอย่างน้อยสองคนที่เข้าใจแต่ละส่วน

## สื่อสารและแก้ความขัดแย้ง

- ตกลงกติกาทีมตั้งแต่ต้น เช่น ตอบแชทภายในเวลาเท่าไร ประชุมเมื่อไร ตัดสินด้วยวิธีใด
- พูดถึงปัญหาและพฤติกรรม ไม่โจมตีตัวคน เช่น "งานส่วนเสียงยังไม่เสร็จ ตอนนี้ติดอะไรอยู่" แทน "เธอขี้เกียจ"
- เมื่อเห็นต่าง ให้กลับไปดูความต้องการของผู้ใช้และข้อมูลจากการทดสอบ ถ้ายังตกลงไม่ได้จึงขอให้ครูช่วย

**การเขียนโปรแกรมเป็นคู่ (pair programming)** ใช้สองคนต่อหนึ่งเครื่อง **คนขับ (driver)** พิมพ์โค้ด **ผู้นำทาง (navigator)** ดูภาพรวม ทักเมื่อเห็นข้อผิดพลาด และคิดกรณีทดสอบ แล้วสลับกันเป็นระยะ ช่วยลดบั๊กและทำให้ความรู้ไม่ติดอยู่กับคนเดียว

## ระบบควบคุมเวอร์ชัน

**ระบบควบคุมเวอร์ชัน (version control)** เช่น Git เก็บประวัติของทุกไฟล์ในโครงงาน แต่ละครั้งที่บันทึกเรียกว่า **คอมมิต (commit)** มีข้อความบอกว่าเปลี่ยนอะไร ย้อนดูหรือกลับไปรุ่นก่อนได้ทุกเมื่อ ที่เก็บโครงงานเรียกว่า **คลัง (repository)** ซึ่งเก็บสำเนาบนเว็บเช่น GitHub ให้ทั้งทีมใช้ร่วมกัน

```bash
git switch -c add-score            # แตกกิ่งใหม่ชื่อ add-score
git add game.py                    # เลือกไฟล์ที่จะบันทึก
git commit -m "เพิ่มตัวนับคะแนน"    # บันทึกพร้อมข้อความ
git push -u origin add-score       # ส่งกิ่งขึ้นคลังกลาง
```

แต่ละคนทำงานบน **กิ่ง (branch)** ของตัวเองโดยไม่กระทบกิ่งหลัก เสร็จแล้วเปิด **คำขอรวม (pull request)** ให้เพื่อนตรวจ แล้วจึง **รวม (merge)** เข้ากิ่งหลัก (ดูภาพ) ถ้าสองคนแก้บรรทัดเดียวกันต่างกัน Git ตัดสินเองไม่ได้ จะเกิด **ความขัดแย้งในการรวม (merge conflict)** และแสดงทั้งสองแบบระหว่างเครื่องหมาย `<<<<<<<`, `=======` และ `>>>>>>>` ให้ทีมเลือกหรือรวมเองแล้วคอมมิตใหม่

**ห้ามคอมมิตรหัสผ่าน กุญแจ API หรือข้อมูลส่วนบุคคล** เพราะประวัติใน Git ลบยาก และคลังสาธารณะใครก็อ่านได้

## ตรวจโค้ดและเขียนเอกสาร

**การตรวจโค้ด (code review)** ให้เพื่อนอ่านโค้ดก่อนรวม โดยดูตามลำดับความสำคัญ

1. ถูกต้องตามข้อกำหนดหรือไม่ รวมกรณีขอบ เช่น ลิสต์ว่าง
2. ปลอดภัยหรือไม่
3. อ่านง่ายหรือไม่ ตั้งชื่อสื่อความหมาย มีเอกสารอธิบาย
4. มีกรณีทดสอบหรือไม่

```python
def average(scores):
    """คืนค่าเฉลี่ยของลิสต์คะแนน ถ้าลิสต์ว่างคืน 0"""
    if len(scores) == 0:
        return 0
    return sum(scores) / len(scores)

print(average([7, 8, 9]))   # 8.0
print(average([]))          # 0
```

ข้อความในเครื่องหมาย `"""` ใต้บรรทัด `def` เรียกว่า **docstring** บอกว่าฟังก์ชันทำอะไร คนในทีมอ่านได้โดยไม่ต้องไล่โค้ด และโครงงานควรมีไฟล์ README บอกวิธีติดตั้ง วิธีใช้ และผู้ร่วมพัฒนา ความเห็นในการตรวจโค้ดควรเจาะจงและสุภาพ ไม่ใช่ "โค้ดแย่"

## ทำงานร่วมกับคนจำนวนมากและต่างที่

เอกสารออนไลน์ที่แก้พร้อมกันได้ ห้องแชท วิดีโอคอล และบอร์ดงานออนไลน์ ช่วยให้ทำงานกับคนต่างโรงเรียน ต่างอาชีพ หรือต่างประเทศได้ ต้องคิดเรื่อง **เขตเวลา** เช่น ประเทศไทยเวลา UTC+7 ญี่ปุ่น UTC+9 นัดประชุม 16:00 ในไทยจึงเป็น 18:00 ที่ญี่ปุ่น ใช้ภาษาที่ชัด และเคารพวัฒนธรรมการทำงานที่ต่างกัน แชร์อย่างรับผิดชอบ ตั้งสิทธิ์ให้เฉพาะคนที่ต้องแก้ ไม่เปิดลิงก์ให้ทุกคนแก้ไขได้

เมื่อต้องการความเห็นหรือข้อมูลจากคนจำนวนมาก ใช้ **แบบสำรวจออนไลน์** หรือ **การระดมจากมวลชน (crowdsourcing)** เช่น วิกิพีเดียและ OpenStreetMap ที่อาสาสมัครทั่วโลกช่วยกันเขียนและวาดแผนที่ คำถามในแบบสำรวจต้องเป็นกลาง ไม่ชี้นำ และควรได้คำตอบจากผู้ใช้หลายกลุ่ม ไม่ใช่เฉพาะเพื่อนในห้อง

## ข้อผิดพลาดที่พบบ่อย

- **ส่งไฟล์ทางแชทแทนการใช้ระบบควบคุมเวอร์ชัน** งานทับกันและหาย
- **คอมมิตข้อความว่า "แก้" หรือ "update"** ย้อนดูแล้วไม่รู้ว่าเปลี่ยนอะไร
- **แบ่งงานแล้วไม่ดูว่างานใดต้องรอกัน** กำหนดเวลาเป็นไปไม่ได้
- **ตรวจโค้ดแค่เรื่องรูปแบบ** มองข้ามบั๊กและกรณีขอบ
- **แบบสำรวจที่ชี้นำ** เช่น "แอปของเราดีมากใช่ไหม"
