## แอปสั่งข้าวที่ไม่มีใครใช้

ชุมนุมคอมพิวเตอร์ใช้เวลาทั้งเทอมเขียนแอปสั่งข้าวกลางวันล่วงหน้าให้โรงอาหาร ทำเสร็จครบทุกเมนูแล้วจึงให้นักเรียนลองใช้ ปรากฏว่าคนส่วนใหญ่หาปุ่มยืนยันไม่เจอ แม่ค้าอยากเห็นยอดรวมของแต่ละเมนูมากกว่ารายชื่อคนสั่ง และผู้ปกครองอยากจ่ายเงินแทนลูก ทั้งที่แก้ได้ไม่ยากถ้ารู้ตั้งแต่สัปดาห์แรก บทนี้ว่าด้วย **กระบวนการพัฒนาโปรแกรม** ที่ฟังผู้ใช้ตลอดทาง ต่อจากบทการออกแบบที่ทุกคนเข้าถึงได้ และใช้วิธีเลือกกรณีทดสอบจากบทออกแบบ ทดสอบ และแก้ข้อผิดพลาด

## วงจรชีวิตของซอฟต์แวร์

ซอฟต์แวร์ทุกชิ้นผ่านงานคล้ายกัน เรียกว่า **วงจรชีวิตของซอฟต์แวร์ (software life cycle)**

1. **เก็บความต้องการ** ใครจะใช้ ใช้ทำอะไร ข้อจำกัดคืออะไร
2. **ออกแบบ** หน้าจอ ข้อมูล และการแบ่งโปรแกรมเป็นฟังก์ชัน
3. **พัฒนา** เขียนโปรแกรม
4. **ทดสอบ** ตรวจว่าทำงานตามข้อกำหนด
5. **นำไปใช้และดูแล** แก้บั๊กและเพิ่มความสามารถตามที่ผู้ใช้ขอ

ถ้าทำทีละขั้นจนจบแล้วค่อยไปขั้นถัดไปเรียกว่า **แบบน้ำตก (waterfall)** เหมาะเมื่อความต้องการชัดและไม่เปลี่ยน เช่น โปรแกรมคำนวณภาษีตามกฎหมาย แต่ถ้ายังไม่แน่ใจว่าผู้ใช้ต้องการอะไร ควรใช้ **แบบวนรอบ (iterative)** คือทำทุกขั้นแบบย่อในรอบสั้น ๆ ได้ชิ้นงานที่ใช้ได้บางส่วน ให้ผู้ใช้ลอง แล้วนำความเห็นไปปรับในรอบถัดไป (ดูภาพ) วิธีแบบ agile ที่บริษัทซอฟต์แวร์นิยมก็ใช้แนวคิดนี้

## สร้างต้นแบบแล้วฟังผู้ใช้

**ต้นแบบ (prototype)** คือรุ่นทดลองที่ทำเร็วและถูก อาจเป็นภาพวาดหน้าจอบนกระดาษ สไลด์ที่กดเปลี่ยนหน้าได้ หรือโปรแกรมที่ทำได้เพียงงานหลักอย่างเดียว จุดประสงค์คือทดสอบความคิดก่อนลงแรงมาก

การฟังผู้ใช้ให้ได้ผล

- **ฟังจากหลายกลุ่ม** แอปสั่งข้าวมีนักเรียน แม่ค้า ครู และผู้ปกครอง แต่ละกลุ่มต้องการต่างกัน รวมถึงผู้ใช้ที่มีข้อจำกัดด้านการมองเห็นหรือใช้โทรศัพท์รุ่นเก่า
- **ให้ลงมือทำงานจริง** เช่น "สั่งข้าวมันไก่หนึ่งจาน" แล้วสังเกตว่าติดตรงไหน ดีกว่าถามว่า "ชอบไหม"
- **วัดผลเป็นตัวเลข** เช่น จำนวนคนที่ทำงานสำเร็จ และเวลาที่ใช้ เพื่อเทียบระหว่างรอบ
- **จัดลำดับความเห็น** ความเห็นมีมากเกินจะทำได้หมด ให้ชั่งผลต่อผู้ใช้กับแรงที่ต้องใช้ ทำเรื่องที่ผลมากแต่แรงน้อยก่อน และพักเรื่องที่ผลน้อยแต่แรงมาก (ดูภาพ)
- **ขอความเห็นจากเพื่อนร่วมทีม** ด้วย คนที่ไม่ได้เขียนส่วนนั้นมักเห็นปัญหาที่คนเขียนมองข้าม

## ต่อยอดโปรแกรมที่มีอยู่

ไม่จำเป็นต้องเริ่มจากศูนย์ทุกครั้ง โปรแกรมของรุ่นพี่หรือโค้ดโอเพนซอร์สนำมาดัดแปลงหรือรวมกับงานของเราได้ ถ้าสัญญาอนุญาตยอมให้ทำ และต้องให้เครดิตเจ้าของเสมอ แต่การแก้โปรแกรมเดิมอาจทำให้ส่วนที่เคยใช้ได้พังโดยไม่ตั้งใจ เช่น เพิ่มส่วนลดสมาชิกแล้วราคาของคนที่ไม่ใช่สมาชิกผิดไปด้วย จึงต้องมี **ชุดกรณีทดสอบ** ที่เขียนจากข้อกำหนด และรันใหม่ทุกครั้งที่แก้ เรียกว่า **การทดสอบถดถอย (regression testing)**

```python
def total_price(items, member=False):
    total = sum(items)
    if member:
        total = total * 0.9     # สมาชิกลด 10%
    return total

# กรณีทดสอบจากข้อกำหนด
assert total_price([40, 15]) == 55               # ไม่ใช่สมาชิก ราคาเดิม
assert total_price([40, 15], member=True) == 49.5
assert total_price([]) == 0                      # ไม่สั่งอะไรเลย
print("ผ่านทุกกรณี")
```

`assert` หยุดโปรแกรมทันทีถ้าเงื่อนไขเป็นเท็จ ชุดทดสอบนี้จึงเตือนได้ทันทีว่าการแก้ครั้งใหม่ทำให้ข้อกำหนดเดิมข้อใดเสีย

## บันทึกเหตุผลของการออกแบบ

อีกหนึ่งปี คนที่มาดูแลแอปต่ออาจสงสัยว่าทำไมปุ่มยืนยันอยู่ล่างจอ ถ้ามี **บันทึกการตัดสินใจ** จะไม่ต้องเดาหรือย้อนไปทำผิดซ้ำ บันทึกที่ดีบอก

- สิ่งที่ตัดสินใจ
- เหตุผลและหลักฐาน เช่น ผลทดสอบกับผู้ใช้
- ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก

นำเสนอได้หลายแบบ เช่น ข้อความสั้น ๆ ภาพหน้าจอก่อนและหลัง ผังงาน หรือวิดีโอสาธิต

## หลายแพลตฟอร์ม หลายภาษา

ผู้ใช้อาจเปิดแอปจากโทรศัพท์ แท็บเล็ต หรือคอมพิวเตอร์ ทางเลือกหนึ่งคือ **เว็บแอป** ที่ปรับหน้าจอตามขนาดอุปกรณ์ เขียนครั้งเดียวใช้ได้ทุกเครื่องที่มีเบราว์เซอร์ อีกทางคือ **แอปเฉพาะระบบ** ที่ใช้กล้อง การแจ้งเตือน และทำงานออฟไลน์ได้ดีกว่า แต่ต้องพัฒนาและทดสอบแยกแต่ละระบบ

ภาษาโปรแกรมก็เลือกตามงาน Python อ่านง่ายและมีไลบรารีวิเคราะห์ข้อมูลมาก JavaScript ทำงานในเบราว์เซอร์ทุกตัว C ทำงานเร็วและใช้หน่วยความจำน้อย เหมาะกับไมโครคอนโทรลเลอร์ SQL ใช้สืบค้นฐานข้อมูล ส่วน Scratch ใช้บล็อกจึงเหมาะกับผู้เริ่มต้น ไม่มีภาษาใดดีที่สุดในทุกงาน

## ข้อผิดพลาดที่พบบ่อย

- **ให้ผู้ใช้เห็นงานครั้งแรกตอนเสร็จแล้ว** แก้ทิศทางได้ยากและแพง
- **ถามแต่เพื่อนสนิท** ได้ความเห็นจากคนกลุ่มเดียวที่คล้ายผู้พัฒนา
- **ทำตามทุกความเห็น** โดยไม่จัดลำดับหรือดูว่าขัดกันเอง
- **แก้โปรแกรมแล้วไม่รันทดสอบเดิม** ส่วนที่เคยใช้ได้พังโดยไม่รู้ตัว
- **ไม่บันทึกเหตุผล** คนรุ่นต่อไปเปลี่ยนกลับไปเป็นแบบที่เคยพิสูจน์แล้วว่าไม่ดี
- **นำโค้ดผู้อื่นมาใช้โดยไม่ดูสัญญาอนุญาตและไม่ให้เครดิต**
