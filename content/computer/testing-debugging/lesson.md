## โปรแกรมที่รันได้ไม่ได้แปลว่าถูกต้อง

ร้านกาแฟเปิดแอปสั่งอาหารใหม่ และพนักงานเห็นว่าระบบคำนวณส่วนลดให้ลูกค้าบางคนผิด โปรแกรมไม่ได้พังและไม่มีข้อความแจ้งเตือน แต่ผลลัพธ์ผิด การทดสอบ (testing) คือการหาความผิดพลาดแบบนี้ก่อนลูกค้าเจอ และการดีบัก (debugging) คือการหาสาเหตุแล้วแก้ไข ทั้งสองอย่างต้องทำอย่างเป็นระบบ

การทดสอบมีสองคำถามที่ต่างกัน **ทวนสอบ (verification)** ถามว่าเราสร้างสิ่งนี้ถูกต้องตามข้อกำหนดหรือไม่ **ตรวจสอบความถูกต้อง (validation)** ถามว่าสิ่งที่สร้างนั้นตรงกับความต้องการของผู้ใช้จริงหรือไม่

## ระดับการทดสอบ

- **การทดสอบหน่วย (unit test)** ทดสอบฟังก์ชันหรือคลาสเดียวโดยแยกออกจากส่วนอื่น
- **การทดสอบบูรณาการ (integration test)** ทดสอบว่าหลายส่วนทำงานร่วมกันได้
- **การทดสอบระบบ (system test)** ทดสอบทั้งโปรแกรมตามข้อกำหนด
- **การทดสอบยอมรับ (acceptance test)** ให้ผู้ใช้หรือผู้มีส่วนได้ส่วนเสียยืนยันว่าใช้งานได้

เมื่อแก้โค้ดแล้วต้องรันชุดทดสอบเดิมทั้งหมดอีกครั้ง เพื่อตรวจว่าสิ่งที่เคยทำงานได้ไม่พังลง เรียกว่า **การทดสอบถดถอย (regression test)**

## ออกแบบกรณีทดสอบจากข้อกำหนด

ฟังก์ชันรับคะแนนสอบต้องอยู่ระหว่าง 0 ถึง 100 ก่อนคิดเกรด ถ้าทดสอบแค่ค่าที่ดูปกติเช่น 75 จะพลาดบั๊กที่เกิดตรงรอยต่อ แนวทางที่ใช้บ่อยมีสี่ข้อ

1. **แบ่งชั้นสมมูล** แบ่งข้อมูลเข้าเป็นกลุ่มที่ควรได้ผลแบบเดียวกัน เช่น ช่วงที่ถูกต้อง ต่ำกว่า 0 สูงกว่า 100 และไม่ใช่ตัวเลข
2. **ค่าขอบ (boundary)** ทดสอบค่าที่อยู่ตรงรอยต่อของแต่ละกลุ่ม เช่น -1, 0, 1, 99, 100, 101
3. **ข้อมูลผิดรูป** ทดสอบค่าที่ไม่ตรงชนิดที่คาดไว้ เช่น ข้อความว่างหรือ None
4. **กรณีข้อผิดพลาด** ตรวจว่าเมื่อข้อมูลไม่ถูกต้อง โปรแกรมโยนข้อยกเว้นหรือแจ้งผลที่ควรเป็น ไม่ใช่คืนค่าผิดเงียบ ๆ

## เขียนชุดทดสอบด้วย assert และ unittest

`assert` ตรวจเงื่อนไขและหยุดทันทีเมื่อเป็นเท็จ ควรใส่ข้อความอธิบายที่บอกค่าที่ใช้และผลที่คาดไว้

```python
def grade(score):
    if score >= 80:
        return "A"
    return "B"

assert grade(80) == "A", "คะแนน 80 ควรได้ A"
assert grade(79) == "B", "คะแนน 79 ควรได้ B"
```

โมดูล `unittest` จัดกรณีทดสอบเป็นคลาสและรันพร้อมกันได้ ผลจะบอกว่ากรณีใดผ่านหรือล้มเหลว

```python
import unittest

class TestGrade(unittest.TestCase):
    def test_boundary(self):
        self.assertEqual(grade(80), "A")
        self.assertEqual(grade(79), "B")

unittest.main(argv=["ignored"], exit=False)
```

ชุดทดสอบที่ดีต้อง **ล้มเหลวเมื่อโค้ดผิด** ไม่ใช่แค่ผ่านเมื่อโค้ดถูก วิธีตรวจชุดทดสอบคือลองแก้โค้ดให้ผิดทีละแบบ เช่น เปลี่ยน `>=` เป็น `>` แล้วดูว่าชุดทดสอบจับได้หรือไม่ ถ้ายังผ่านอยู่แสดงว่ายังขาดกรณีทดสอบ

## กล่องดำและกล่องขาว

การทดสอบ**กล่องดำ** ดูเฉพาะข้อกำหนดและผลลัพธ์ที่ได้ ไม่สนโครงสร้างภายใน การทดสอบ**กล่องขาว** ใช้ความรู้ของโค้ดภายในเพื่อเลือกกรณีที่ไปถึงเส้นทางต่าง ๆ **การครอบคลุมโค้ด (coverage)** บอกสัดส่วนของคำสั่งที่ถูกรันจากชุดทดสอบ แต่การครอบคลุม 100% ไม่ได้แปลว่าไม่มีบั๊ก เพราะค่าที่ทดสอบอาจไม่ครอบคลุมกรณีที่ผิดได้

ฟังก์ชันควรมี **docstring** ที่บอกข้อกำหนด เช่น รับอะไร คืนอะไร และโยนข้อยกเว้นเมื่อใด เพื่อให้การออกแบบกรณีทดสอบอ้างอิงได้

## ดีบักอย่างเป็นระบบ

ขั้นแรกทำให้บั๊กเกิดซ้ำได้ด้วยข้อมูลเข้าที่แน่นอน ถ้าเกิดซ้ำไม่ได้ก็หาสาเหตุไม่ได้ จากนั้นแบ่งโค้ดด้วยการ**แบ่งครึ่ง (bisect)** เช่น พิมพ์ค่าตรงกลางของขั้นตอนแล้วดูว่าค่าถูกหรือผิดก่อนจุดนั้น ทำซ้ำจนแคบลงถึงบรรทัดที่ผิด การแบ่งครึ่งทำให้ต้องตรวจเพียงไม่กี่ครั้ง แม้โค้ดยาว

ตัวดีบักใน IDE ช่วยตั้ง **จุดพัก (breakpoint)** หยุดโปรแกรมตรงบรรทัดที่สนใจ ดูค่าตัวแปร ทำทีละบรรทัด และดู **กองการเรียก (call stack)** ว่าฟังก์ชันใดเรียกฟังก์ชันใดมาถึงจุดนี้

เมื่อโปรแกรมล้มเหลว Python แสดง **traceback** ซึ่งไล่ชื่อไฟล์และบรรทัดจากจุดเรียกภายนอกไปถึงจุดที่เกิดข้อผิดพลาด ให้อ่านจากล่างขึ้นบนเพื่อหาบรรทัดที่เกิดข้อยกเว้นจริง แล้วค่อยไล่กลับไปดูว่าใครเป็นผู้ส่งค่าที่ผิดเข้ามา

## ตัวอย่างการทดสอบค่าขอบ

สมมติเกณฑ์เกรดคือ 50, 60, 70 และ 80 ถ้าทดสอบเฉพาะค่าที่อยู่กลางช่วงอย่าง 65 จะไม่พบว่าโค้ดเขียน `>` ผิดแทน `>=` ที่เกณฑ์ 60 ควรทดสอบค่าที่เป็นเกณฑ์เองและค่าที่ต่ำกว่าเกณฑ์หนึ่งหน่วย

## บันทึกบั๊ก

รายงานบั๊กที่ดีควรระบุข้อมูลเข้าที่ทำให้เกิดซ้ำได้ ผลที่ได้ ผลที่คาดไว้ และเวอร์ชันของโค้ด ให้คนอื่นทำซ้ำได้โดยไม่ต้องเดา

## ข้อผิดพลาดที่พบบ่อย

- ทดสอบเฉพาะกรณีที่คิดว่าจะถูก แล้วสรุปว่าโปรแกรมไม่มีบั๊ก
- เขียน `assert` ที่ตรวจแค่ว่าได้ค่าอะไรก็ได้ โดยไม่เทียบกับค่าที่ถูก
- แก้บั๊กแล้วไม่รันชุดทดสอบเดิม ทำให้บั๊กใหม่แฝงอยู่
- แก้อาการที่เห็นโดยไม่หาสาเหตุ บั๊กจึงกลับมาอีกในรูปแบบอื่น
