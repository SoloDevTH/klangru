## โปรแกรมที่ทำงานถูกต้องอาจยังไม่ปลอดภัย

ระบบสมาชิกของร้านกาแฟเก็บชื่อ เบอร์โทร และประวัติการสั่งซื้อของลูกค้า โปรแกรมทำงานได้ดีในวันที่ทดลอง แต่ถ้ามีคนพิมพ์ข้อมูลแปลก ๆ ลงในช่องกรอก หรือเข้าหน้าที่ไม่ควรเข้าได้ ข้อมูลลูกค้าอาจรั่วไหลหรือถูกแก้ไขได้ **การเขียนโค้ดอย่างปลอดภัย** คือการคิดตั้งแต่ต้นว่าใครจะพยายามทำอะไรกับระบบ และป้องกันจุดอ่อนนั้นไว้ล่วงหน้า

บทนี้อธิบายหลักการและแนวปฏิบัติ ไม่ได้สอนวิธีโจมตีระบบ เพราะจุดประสงค์คือให้เห็นว่าจะป้องกันอย่างไร

## ช่องโหว่ที่พบบ่อย

**การแทรกคำสั่ง (injection)** เกิดเมื่อข้อมูลที่ผู้ใช้กรอกถูกนำไปต่อเข้าเป็นส่วนหนึ่งของคำสั่ง เช่น คำสั่ง SQL หรือคำสั่งของระบบปฏิบัติการ ทำให้ข้อมูลนั้นกลายเป็นคำสั่งและเปลี่ยนความหมายของคำสั่งเดิมได้ วิธีป้องกันคือแยกคำสั่งออกจากข้อมูลเสมอ

**สคริปต์ข้ามเว็บ (XSS)** เกิดเมื่อข้อความที่ผู้ใช้กรอกถูกแสดงในหน้าเว็บโดยไม่หลีกอักขระ เบราว์เซอร์จึงอาจตีความข้อความนั้นเป็นโค้ด วิธีป้องกันคือหลีกอักขระพิเศษ เช่น `<` และ `&` ก่อนแสดงผล

**การตรวจสิทธิ์ที่ขาดหาย** เกิดเมื่อระบบรู้ว่าผู้ใช้เป็นใคร แต่ไม่ตรวจว่าผู้ใช้นั้นมีสิทธิ์เข้าถึงข้อมูลนี้หรือไม่ เช่น เปลี่ยนรหัสประจำตัวในลิงก์แล้วเห็นข้อมูลของคนอื่น

**ความลับฝังในโค้ด** เช่น รหัสผ่านหรือกุญแจ API ที่เขียนไว้ในซอร์สโค้ด เมื่อโค้ดถูกแชร์หรือบันทึกในประวัติของระบบควบคุมเวอร์ชัน ความลับนั้นก็รั่วไปด้วย

**บัฟเฟอร์ล้น (buffer overflow)** เป็นช่องโหว่ในภาษาที่จัดการหน่วยความจำเอง เมื่อเขียนข้อมูลเกินขนาดที่จองไว้ ข้อมูลอาจทับส่วนอื่นของหน่วยความจำ ภาษาอย่าง Python จัดการขนาดให้อัตโนมัติ จึงไม่ค่อยพบแบบนี้ แต่หลักการตรวจขนาดข้อมูลยังใช้ได้กับทุกภาษา

## ตรวจข้อมูลเข้าด้วยรายการที่อนุญาต

การตรวจข้อมูลเข้ามีสองแนวทาง **รายการที่อนุญาต (allowlist)** กำหนดว่าอะไรยอมรับได้ ส่วน **รายการที่ห้าม (denylist)** พยายามระบุว่าอะไรต้องปฏิเสธ แนวทางแรกปลอดภัยกว่า เพราะรูปแบบที่ไม่เคยคิดถึงจะถูกปฏิเสธโดยอัตโนมัติ ส่วนรายการห้ามมักตกหล่นรูปแบบใหม่

ชื่อผู้ใช้ควรตรวจทั้งชนิด ความยาว และรูปแบบ เช่น ยาว 3 ถึง 16 ตัวอักษร ขึ้นต้นด้วยตัวอักษร และมีเฉพาะตัวอักษร ตัวเลข หรือขีดล่าง ข้อมูลที่ไม่ผ่านให้ปฏิเสธทั้งหมดพร้อมข้อความที่เข้าใจได้ ไม่ควรพยายามแก้ไขข้อมูลที่ผิดเองเงียบ ๆ

## แยกคำสั่งออกจากข้อมูล

เมื่อต้องส่งข้อมูลเข้าคำสั่งฐานข้อมูล ใช้**พารามิเตอร์ (parameter)** ซึ่งมีตัวเว้นที่ระบบฐานข้อมูลเติมค่าให้ โดยโครงสร้างคำสั่งถูกส่งแยกต่างหากจากค่าข้อมูล ระบบจึงไม่ตีความข้อมูลเป็นคำสั่ง

```python
sql = "SELECT total FROM orders WHERE order_no = ?"
params = (1024,)    # ค่าถูกส่งแยก ไม่ได้ต่อเข้าไปในสตริง SQL
```

การแสดงผลในหน้าเว็บก็แยกแบบเดียวกัน ต้องหลีกอักขระตามบริบทที่ข้อมูลจะไปแสดง เช่น หลีกอักขระแบบ HTML ก่อนวางในหน้า HTML

## หลักการออกแบบที่ปลอดภัย

- **สิทธิ์น้อยที่สุด (least privilege)** ให้สิทธิ์แต่ละบัญชีเท่าที่หน้าที่ต้องใช้ พนักงานคิดเงินไม่จำเป็นต้องแก้ราคาเมนู
- **ค่าเริ่มต้นที่ปลอดภัย (secure default)** เมื่อไม่ได้ตั้งค่าอะไร ระบบควรปฏิเสธการเข้าถึงก่อน
- **ล้มเหลวอย่างปลอดภัย (fail securely)** เมื่อการตรวจสิทธิ์พัง ให้ปฏิเสธ ไม่ใช่เปิดให้ผ่าน
- **ป้องกันหลายชั้น (defense in depth)** ตรวจข้อมูลที่ขอบระบบ และตรวจซ้ำที่จุดที่ใช้งานจริง
- **ลดพื้นผิวการโจมตี** เปิดเฉพาะบริการและฟังก์ชันที่จำเป็น ลบโค้ดที่ไม่ได้ใช้

## วงจรพัฒนาที่ปลอดภัย

การคิดเรื่องความปลอดภัยควรเริ่มก่อนเขียนโค้ด การทำ **แบบจำลองภัยคุกคาม (threat model)** ช่วยตอบคำถามสามข้อ คือมีทรัพย์สินอะไรที่ต้องดูแล ใครอาจเป็นผู้โจมตี และระบบมีจุดเข้าถึงใดบ้าง จากนั้นจึงเลือกการป้องกันให้ตรงกับความเสี่ยงที่สำคัญที่สุด

ระหว่างพัฒนาควรใช้ **การทบทวนโค้ด (code review)** และเครื่องมือวิเคราะห์โค้ดแบบสถิต (static analysis) ที่ตรวจรูปแบบโค้ดที่อันตรายได้อัตโนมัติ หลังจากนั้นควรเขียนชุดทดสอบด้านความปลอดภัย เช่น ทดสอบว่าข้อมูลที่ผิดรูปถูกปฏิเสธจริง และทดสอบว่าผู้ใช้คนหนึ่งเข้าถึงข้อมูลของอีกคนไม่ได้

## ข้อผิดพลาดที่พบบ่อย

- คิดว่าการตรวจด้วยรายการห้ามเพียงพอ แล้วพบรูปแบบที่ตกหล่นภายหลัง
- ต่อข้อมูลของผู้ใช้เข้ากับสตริงคำสั่ง แทนการใช้พารามิเตอร์
- เก็บรหัสผ่านเป็นข้อความธรรมดาหรือฝังความลับไว้ในโค้ด
- แสดงข้อความ error ที่มีชื่อตารางหรือรายละเอียดภายในให้ผู้ใช้ทั่วไปเห็น
- ตรวจสิทธิ์เฉพาะที่หน้าจอ แต่ไม่ตรวจที่ฝั่งเซิร์ฟเวอร์เมื่อมีคำขอจริง
